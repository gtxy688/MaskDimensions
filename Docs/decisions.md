# 技术选型决策记录（decisions.md）

> 本文件给**用户查阅**：为什么这个项目用这套技术，而不是别的。
> 每个决策都按「X 是什么 / Y 是什么 / 为什么选 X」写，新手友好。
> AI 编写脚本时**不要**把本文件当规范用——写代码看 `Docs/architecture/`，验收看 `Docs/tests/`。

---

## 总览：本项目与只狼项目的差异化分工

| | 只狼复刻项目 | Mask Dimensions（本项目） |
|---|---|---|
| 类型 | 3D 动作战斗 | 2D 平台跳跃 + 维度切换 |
| 技术主场 | 3D 角色控制/战斗、Boss AI、HFSM、动画事件、命中判定 | **自研 2D 确定性物理**、**维度渲染差异化** |
| 面试卖点 | 战斗系统深度 | 物理底层深度 + 视觉技术 |

两个项目刻意错开，避免简历上"两个项目都在讲状态机"。

## D1：玩家物理 —— 自研运动学控制器 vs Rigidbody2D

- **X 是什么（选了它）**：自研运动学物理框架 `Kinematic2D`。自己用射线扫描（Raycast）检测碰撞、自己解算位移。玩家不再依赖 Unity 物理引擎。
- **Y 是什么（没选它）**：
  - Y1：Rigidbody2D 动态刚体（项目现状）——由 Unity 物理引擎积分位置，代码只给速度/力。
  - Y2：Rigidbody2D 运动学体（isKinematic）——不参与力模拟，但仍依赖引擎的碰撞回调。
- **为什么选 X**：
  1. **确定性**：位移完全由自己的代码决定，没有引擎浮点积分、没有"撞到东西被弹开"的不可控行为，手感可以精确复现；
  2. **平台跳跃是"手感行业"**：土狼时间、跳缓冲这类高级手感，在动态刚体上要做很多对抗引擎的 hack（调 gravity scale、锁速度）；自研物理直接读"碰撞结果"就能实现；
  3. **面试叙事**："我从零实现了一个 2D 运动学控制器"是少数应届生能讲清楚的话题，Rigidbody2D 是人人都会用的引擎黑盒；
  4. **与维度系统契合**：射线扫描天然支持"我自己的射线过滤掉另一个维度的物体"（见 D3），这是 Rigidbody2D 做起来很别扭的。

## D2：物理框架 —— 从零重写 vs 复活现有教程代码

- **X 是什么（选了它）**：从零重写。不沿用项目里现存的 `RaycastController2D` / `PlayerPhysicsController2D`（它们是一套完整的射线控制器，但从未被使用，是死代码）。
- **Y 是什么（没选它）**：复活那套死代码，修修补补后接入玩家。
- **为什么选 X**：
  1. 那套代码是经典教程结构（网上广为流传的 Sebastien Lague 风格），**面试官一眼就能认出**——"自研物理"的叙事当场破产；
  2. 从零重写逼自己真正吃透碰撞迭代、斜坡换算、单向板规则的**第一性原理**——面试追问时能现场推导而不是背诵；
  3. 死代码本身是简历红旗（"为什么有个没用的物理控制器？"），删掉它顺便清掉这个雷；
  4. 新框架的 API 为维度切换量身设计（过滤器注入），教程代码没有这个概念。

---

## D3：维度碰撞 —— 射线级过滤器 vs IgnoreLayerCollision

- **X 是什么（选了它）**：`ICollisionFilter`。玩家每发射线命中物体后，问过滤器"这个物体在当前维度可见吗？"不可见就忽略这次命中。维度切换 = 给玩家换一个过滤器。
- **Y 是什么（没选它）**：`Physics2D.IgnoreLayerCollision`（项目现状）——修改物理引擎的**全局静态开关**，让某两个 Layer 之间不再碰撞。
- **为什么选 X**：
  1. Y 是**全局**的：它影响场景里所有物体，不只是玩家。敌人子弹、其他角色都受影响，多关卡时容易互相污染；
  2. Y 是**状态**不是**查询**：改完引擎状态，代码里其他地方想确认"现在谁和谁不碰"得读全局配置；
  3. X 是**局部**的：只影响玩家自己的射线，干净、可预测；
  4. **面试扩展题**"如果做双人模式怎么办"：Y 直接崩（一个玩家在表世界一个在里世界，全局开关没法表达），X 每个玩家注入自己的过滤器即可——这个答案在面试里很值钱。

## D4：地面检测 —— 读碰撞结果 vs OverlapBox

- **X 是什么（选了它）**：直接读 `KinematicBody` 的碰撞结果（`CollisionResult.IsGrounded`）——地面有没有，是物理层解算时自己算出来的。
- **Y 是什么（没选它）**：`Physics2D.OverlapBox`（项目现状）——在地面检测点画个盒子查物理引擎有没有东西，命中后再手工排除"另一维度的层"（双重世界排除 hack）。
- **为什么选 X**：
  1. Y 是"补丁叠补丁"：检测完还要按 layer 再过滤一次，逻辑散落两处；
  2. X 的信息来自同一套射线系统，天然一致：站在斜坡上、站在单向板上、站在移动平台上，碰撞结果都正确，不需要针对每种情况写特判；
  3. 删掉 Y 顺便删掉那个"双重世界排除"的 hack，代码量减少、可读性提高。

## D5：后处理 —— URP Volume vs PPv2（旧后处理）

- **X 是什么（选了它）**：URP 原生的 Volume 后处理体系（Unity 现代渲染管线的标准方案），所有滤镜/过渡都用它。
- **Y 是什么（没选它）**：`com.unity.postprocessing`（PPv2，项目现状）——上一代后处理方案，和 URP 并存。
- **为什么选 X**：
  1. 项目已启用 URP，PPv2 与 URP 并存会导致**双份后处理互相干扰**、兼容问题；
  2. 本项目渲染线的其他部分（2D 光照、Renderer Feature）都是 URP 生态，统一用 Volume 才能让三者在**同一套框架**里协同（比如切换时 Volume weight 过渡和 Renderer Feature 转场同时播放）；
  3. 面试答"为什么统一 URP"比答"为什么两套后处理都在"容易得多。

## D6：世界视觉 —— 双 Volume 权重过渡 vs 硬切

- **X 是什么（选了它）**：两个 Volume（表世界滤镜、里世界滤镜），切换瞬间用 **weight 交叉淡化**过渡，配合顿帧形成"断片感"。
- **Y 是什么（没选它）**：切换瞬间直接换滤镜参数（项目现状是 `MaskPostProcessingManager` 用协程 lerp 饱和度和曝光——单 Volume 改参数）。
- **为什么选 X**：
  1. 双 Volume 是 URP 推荐的"场景氛围切换"做法，weight 过渡平滑、可调曲线、可叠加；
  2. 现有单 Volume lerp 方案只能改"数值"，不能表达"两套完全不同视觉风格"（噪点/扫描线/扭曲这类需要开/关组件的差异，weight 更干净）；
  3. 面试可讲：两个 Volume 的 weight 由切换协程用 `Time.unscaledDeltaTime` 驱动——和顿帧（timeScale=0）正确协作。

## D7：光照 —— URP 2D Light vs 假光（后处理调亮度）

- **X 是什么（选了它）**：URP 2D Light 真实光照——表世界明亮全局光，里世界昏暗 + 局部光源（如玩家手持灯），物体有真实明暗层次。
- **Y 是什么（没选它）**：只用后处理把里世界调暗（假光）——没有光源遮挡、没有明暗层次，只是"套了个滤镜"。
- **为什么选 X**：
  1. 真实光照产生"遮挡感"和"层次感"（光被墙挡住、光源照亮的范围），这是平台跳跃关卡信息传达的重要手段（玩家靠光判断危险/安全）；
  2. 2D Light 是 URP 特色技术，面试有料可讲（法线贴图、光照遮罩、光源类型）；
  3. 与后处理配合（暗环境 + 噪点滤镜）才能做出"里世界压抑感"，单独调亮度做不到。

---

## D8：切换转场 —— 自写 Renderer Feature vs 现成插件

- **X 是什么（选了它）**：自己写 Renderer Feature + Shader（如扫屏转场/撕裂效果）。
- **Y 是什么（没选它）**：Asset Store 现成转场插件/特效资源。
- **为什么选 X**：
  1. 自写 = 展示 **ScriptableRenderPass / CommandBuffer / Shader 功底**，这是大厂客户端面试的硬通货；
  2. 现成插件没有技术含量，简历写不出亮点，面试也问不出深度；
  3. 转场效果与维度切换时机深度耦合（顿帧期间播放），自写才能精确控制时机。

---

## D9：关卡 —— 全部重做 vs 修补旧 3 关

- **X 是什么（选了它）**：3 关全部推倒重做，围绕新物理能力（斜坡/单向板/动量）与视觉设计。
- **Y 是什么（没选它）**：保留旧关卡结构，只改代码。
- **为什么选 X**：
  1. 旧关卡按 Rigidbody2D 手感设计，换成自研物理后手感完全不同，硬留旧关 = 玩法与物理不匹配；
  2. 关卡是"秀技术"的舞台，必须设计"只能靠新机制才能过"的瞬间，否则新技术没有展示机会；
  3. 内容量小（3 关），重做成本可控。

---

## D10：工程层 —— 不做测试/CI（档次 A）vs 全套工程化

- **X 是什么（选了它）**：不做自动化测试、不做 CI、不做 asmdef 分层。验证靠**人工验收清单**（`Docs/tests/`）。
- **Y 是什么（没选它）**：单元测试 + GitHub CI + 程序集分层（档次 C，完整工程化）。
- **为什么选 X**：
  1. 本项目是秋招作品，**面试深度 > 工程完备度**：面试官更想听"物理怎么实现的"而不是"你怎么配 CI 的"；
  2. 时间预算有限，工程层会吃掉物理/渲染打穿的精力；
  3. 人工验收清单（用户逐条验证）已能满足"可验证"需求，且是只狼项目验证过的成熟工作流；
  4. 后续若时间富余，可再补 CI（有 git 历史，随时可加）。

---

## D11：对象池 —— 保留但降级

- **X 是什么（选了它）**：`ObjectPool<T>` 代码保留（它实现质量确实高：Prewarm/容量上限/防重复入池），但**从简历卖点中降级**——不主动讲，除非补上真实性能数据。
- **Y 是什么（没选它）**：把对象池作为核心卖点写进简历（项目现状的叙事）。
- **为什么选 X**：
  1. 本项目子弹量小，**根本不存在 GC 压力**——对象池是"解决不存在的问题"，面试官一问"你测过 GC 吗"就露馅；
  2. 保留代码是合理的（防未来扩展），但叙事上不能吹；
  3. 若想重新启用为卖点，需要先测真实数据（Profiler 对比），有数据才能讲。

---

## D12：玩家状态机 —— 保留不重做

- **X 是什么（选了它）**：保留现有状态机（字典注册表 + BaseState 生命周期 + 白名单切换）。
- **Y 是什么（没选它）**：升级为 HFSM（层次状态机）或重写状态管理。
- **为什么选 X**：
  1. HFSM 是**只狼项目的主场**，本项目再做一遍 = 两个项目重复叙事；
  2. 本项目的差异化在物理与渲染，状态机够用即可（YAGNI）；
  3. 现有状态机质量可用（依赖注入、白名单防非法切换），不值得为重构而重构。
